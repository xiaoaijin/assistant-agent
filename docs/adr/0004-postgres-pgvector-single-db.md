# PostgreSQL + pgvector，单库承载关系数据与向量

数据与向量检索都用 PostgreSQL（向量列 `vector(1024)`，余弦检索），不引入独立向量库。客服知识库（FAQ、售后政策）的规模和召回要求初期用不了专用向量库的生态优势，而"一个库管所有状态"直接支撑了本项目的核心设计——会话、审批、循环状态全部落库可恢复（ADR-0002），跨库一致性是不必要的复杂度。参考 AutoGPT：UnifiedContentEmbedding 统一嵌入表 + ContentType 枚举扩展 + 原生 SQL 余弦查询，借鉴其建模（RAG 具体设计见 ADR-0005）。若未来召回质量或规模成为瓶颈，迁移成本集中在嵌入相关表，可逆。

## Consequences

- 文档切片、召回评估需要自建（AutoGPT 只有嵌入表和查询函数）
- 嵌入模型换型需要重灌向量列，模型选型要趁早定

## 修订（2026-11-10，RAG 设计确认时）

- **维度 1536 → 1024**：原 1536 照搬 AutoGPT 的 text-embedding-3-small；确认中文知识库场景后改用通义 `text-embedding-v3`（1024 维），中文检索质量更好且 LiteLLM 换供应商零成本。趁表未建改列，成本为零。
- **建模落点**：不是单张统一嵌入表，而是 `knowledge_documents`（原文）+ `knowledge_chunks`（切片文本 + embedding 列）两表。原因：文档原文必须落库（管理页展示/编辑、换模型重切片重灌都依赖原文），单表方案没有原文的位置；`content_type` 枚举照样存在，"扩知识类型 = 插行"的借鉴点保留。
